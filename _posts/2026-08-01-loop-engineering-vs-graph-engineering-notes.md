## 한 줄 요약
**루프 엔지니어링은 한 에이전트가 스스로 계획·실행·검증·수정하도록 반복 구조를 만드는 일이고, 그래프 엔지니어링은 여러 에이전트와 단계들을 역할별로 연결해 전체 협업 구조를 설계하는 일에 가깝습니다.**

## 왜 이 글을 남기나
요즘 AI 관련 글을 보다 보면 `프롬프트 엔지니어링`, `컨텍스트 엔지니어링`, `하네스 엔지니어링`, `루프 엔지니어링`, `그래프 엔지니어링` 같은 말이 너무 빠르게 늘어납니다.

그런데 막상 읽어 보면 이름은 많아도 헷갈리는 지점은 비슷합니다.

- 도대체 뭐가 새 개념인지
- 어디까지가 진짜 실무 차이고 어디까지가 유행어인지
- 내가 지금 만들려는 자동화나 에이전트 시스템에 어떤 관점이 더 맞는지

이번에는 그중에서도 **루프 엔지니어링(loop engineering)** 과 **그래프 엔지니어링(graph engineering)** 을 중심으로, 실제로 어떤 차이를 말하는지 공부용으로 다시 정리해 봤습니다.

중요한 전제도 하나 있습니다.

이 두 용어는 아직 전통적인 소프트웨어 공학 용어처럼 완전히 표준화된 개념은 아닙니다. 특히 **그래프 엔지니어링** 은 2026년 중반 AI 에이전트 커뮤니티에서 빠르게 떠오른 표현에 가깝고, 문맥에 따라 **지식 그래프(knowledge graph)** 와 헷갈릴 수 있습니다. 그래서 이 글은 “엄밀한 교과서 정의”보다는, **최근 에이전트 실무 문맥에서 사람들이 이 말을 어떻게 쓰는지** 를 중심으로 정리합니다.

## 먼저 큰 그림부터
제가 이해한 가장 쉬운 구분은 이렇습니다.

### 루프 엔지니어링
> **한 명의 유능한 작업자가 일을 끝낼 때까지 스스로 반복하도록 만드는 설계**

### 그래프 엔지니어링
> **여러 작업자와 검토자, 라우터, 승인자, 도구 호출 단계를 연결해 팀처럼 움직이게 만드는 설계**

조금 더 단순하게 말하면,

- 루프 엔지니어링은 **반복의 설계**
- 그래프 엔지니어링은 **구조와 연결의 설계**

라고 볼 수 있습니다.

## 루프 엔지니어링이란 무엇인가
IBM은 루프 엔지니어링을 **AI 에이전트가 최소한의 인간 개입으로 목표를 향해 반복적으로 행동·관찰·조정하도록 만드는 설계**로 설명합니다. 핵심은 사람이 매번 다음 프롬프트를 쓰는 대신, **에이전트가 스스로 다음 행동을 이어 가게 만드는 실행 시스템**을 설계하는 쪽으로 개발자의 역할이 이동한다는 점입니다.

이 말이 중요한 이유는, AI 사용 방식이 다음처럼 바뀐다는 뜻이기 때문입니다.

### 예전 방식
1. 사람이 프롬프트를 쓴다.
2. 모델이 답한다.
3. 사람이 보고 다시 프롬프트를 쓴다.
4. 이 과정을 계속 반복한다.

### 루프 방식
1. 사람이 목표와 종료 조건을 준다.
2. 에이전트가 계획한다.
3. 도구를 써서 실행한다.
4. 결과를 확인한다.
5. 실패하면 스스로 수정한다.
6. 성공 조건이 충족될 때까지 반복한다.

즉, **사람이 매 턴을 직접 운전하던 구조를, 목표와 검증 기준만 정하고 시스템이 반복 운전하도록 바꾸는 것**이 루프 엔지니어링의 핵심입니다.

## 루프의 기본 모양
LangChain은 에이전트의 가장 기본적인 형태를 **“모델이 도구를 호출하는 루프”** 로 설명합니다. IBM도 비슷하게 루프의 단계를 다음처럼 정리합니다.

1. **Goal** — 무엇이 끝난 상태인지 정의
2. **Action** — 목표에 가까워지기 위한 행동 수행
3. **Observation** — 결과를 읽고 확인
4. **Adjustment** — 필요하면 접근을 수정

이 구조를 한국어로 아주 평범하게 바꾸면,

- 목표를 세우고
- 해 보고
- 결과를 보고
- 틀리면 고치고
- 될 때까지 반복한다

정도가 됩니다.

그래서 루프 엔지니어링은 사실 거창한 새 이론이라기보다, **좋은 개발 습관을 에이전트 실행 구조로 옮기는 일**에 더 가깝습니다.

## 루프 엔지니어링이 중요한 이유
제가 조사하면서 가장 크게 남은 포인트는, 루프 엔지니어링이 결국 **프롬프트 품질보다 피드백 구조를 더 중요하게 본다**는 점이었습니다.

좋은 루프는 단순히 “잘 써줘”라고 부탁하지 않습니다. 대신 이런 것들을 시스템에 넣습니다.

- 언제 멈출지
- 무엇을 통과해야 성공인지
- 실패했을 때 무엇을 다시 시도할지
- 어떤 도구를 쓸 수 있는지
- 사람이 어디서 승인할지
- 작업 기록을 어디에 남길지

Addy Osmani는 이걸 굉장히 실무적으로 설명합니다. 그의 요지는 간단합니다.

> 더 이상 사람이 매번 코딩 에이전트에게 직접 프롬프트를 넣는 게 아니라, **일을 찾고, 할당하고, 확인하고, 상태를 남기고, 다음 행동을 결정하는 작은 시스템 자체를 설계하는 쪽으로 이동하고 있다**는 것입니다.

이 관점에서 보면 루프 엔지니어링은 다음 같은 조각들의 결합입니다.

- 자동 실행 스케줄
- 병렬 작업을 위한 작업 분리
- 프로젝트 지식을 담은 스킬/문서
- 외부 도구 연결
- 검증용 서브에이전트
- 디스크나 이슈 보드에 남는 상태 기록

즉 루프는 단순히 `while` 문 같은 게 아니라, **에이전트가 장기적으로 일을 이어 가기 위한 운영 구조**입니다.

## 루프 엔지니어링을 한 문장으로 다시 말하면
제가 이번에 내린 개인적인 요약은 이렇습니다.

> **루프 엔지니어링은 에이전트에게 “한 번 답하고 끝내지 말고, 목표를 만족할 때까지 일하고 확인하고 고쳐라”라는 실행 환경을 설계하는 일이다.**

## 그래프 엔지니어링이란 무엇인가
그래프 엔지니어링은 루프 엔지니어링보다 조금 더 최근에 많이 회자된 표현입니다.

LangChain은 에이전트 시스템을 그래프로 표현하는 방식을 꽤 오래 다뤄 왔고, 2026년 7월 글에서는 **그래프 엔지니어링은 새로운 발명이라기보다, 믿을 만한 에이전트를 만들기 위해 이미 해 오던 그래프 기반 오케스트레이션에 새 이름이 붙은 것**에 가깝다고 설명합니다.

핵심은 이것입니다.

- **노드(node)** 는 일을 하는 단위입니다.
  - 결정적 코드
  - 단일 LLM 호출
  - 도구 호출
  - 내부 루프를 가진 에이전트 전체
- **엣지(edge)** 는 다음에 어디로 갈지 정합니다.
  - 항상 같은 경로로 갈 수도 있고
  - 조건에 따라 다른 경로로 갈 수도 있고
  - 여러 작업으로 병렬 분기했다가 다시 합칠 수도 있습니다.

TrueFoundry의 설명을 빌리면, 그래프 엔지니어링은 **다중 에이전트 시스템의 topology(구조)** 를 설계하는 일입니다. 즉,

- 어떤 역할의 노드가 존재하는지
- 누가 누구와 통신할 수 있는지
- 어떤 단계에서 사람 승인이 필요한지
- 어떤 작업은 병렬로 보내고 어떤 작업은 반드시 순서대로 보내는지
- 어떤 상태가 단계 사이를 흘러다니는지

를 **명시적인 구조물로 다루는 것**에 가깝습니다.

## 중요한 오해 하나: 지식 그래프와는 다르다
여기서 꼭 분리해야 할 게 있습니다.

**그래프 엔지니어링** 이라고 해서 항상 **지식 그래프** 를 뜻하는 건 아닙니다.

- **지식 그래프**: 엔티티와 관계를 데이터 구조로 표현해 “무엇을 아는가”를 정리
- **그래프 엔지니어링(에이전트 문맥)**: 역할, 단계, 위임 경로, 승인 경로를 구조로 표현해 “어떻게 일하는가”를 설계

둘은 함께 쓸 수는 있어도 질문이 다릅니다.

- 지식 그래프는 **지식의 구조**
- 그래프 엔지니어링은 **작업 조직의 구조**

입니다.

## 왜 그래프라는 말이 나오기 시작했을까
단일 루프는 강력하지만, 실제로 작업이 커지면 한계가 생깁니다.

예를 들어 하나의 에이전트에게 아래를 다 맡긴다고 생각해 보면,

- 요구사항 읽기
- 관련 코드 찾기
- 구현하기
- 테스트 돌리기
- 실패 원인 분석하기
- 보안 검토하기
- PR 설명 쓰기

처음에는 가능해 보여도 점점 이런 문제가 생깁니다.

- 컨텍스트가 너무 비대해짐
- 한 에이전트가 너무 많은 역할을 떠안음
- 검토와 작성이 같은 머리에서 일어남
- 어떤 단계가 실패했는지 추적이 어려움
- 병렬화가 잘 안 됨

그래서 등장하는 생각이 바로 이것입니다.

> “한 명이 모든 걸 다 하게 하지 말고, **역할을 쪼개고 연결 구조를 설계하자.**”

이때 필요한 관점이 그래프 엔지니어링입니다.

## 그래프 엔지니어링을 쉽게 비유하면
### 루프 엔지니어링의 비유
혼자 일 잘하는 개발자 한 명이 있습니다.

- 일감을 받고
- 직접 조사하고
- 구현하고
- 테스트하고
- 문제 있으면 다시 고칩니다.

이 사람의 **작업 습관과 반복 방식**을 설계하는 게 루프 엔지니어링입니다.

### 그래프 엔지니어링의 비유
이제 팀이 있습니다.

- 접수 담당
- 설계 담당
- 구현 담당
- 검토 담당
- 승인 담당

이들이 **누구에게 어떤 순서로 일이 넘어가고**, 어떤 경우엔 병렬로 진행되고, 어디서 사람 승인이 들어가는지 설계하는 게 그래프 엔지니어링입니다.

즉,

- 루프는 **개인의 작업 사이클**
- 그래프는 **팀의 협업 구조**

라고 보면 이해가 훨씬 쉽습니다.

## 루프와 그래프는 경쟁 관계가 아니다
이 부분이 제일 중요했습니다.

LangChain 글에서 가장 인상적이었던 문장은 사실상 이것이었습니다.

> **루프는 단순한 그래프다.**

즉 루프와 그래프는 서로 대체 관계라기보다, **스케일이 다른 관점**입니다.

- 루프는 하나의 순환 구조를 강조한 표현이고
- 그래프는 여러 노드와 전이까지 포함한 더 넓은 표현입니다.

그래서 관계를 이렇게 보는 게 제일 자연스럽습니다.

1. **프롬프트 엔지니어링** — 한 번의 지시를 잘 쓰는 문제
2. **루프 엔지니어링** — 한 에이전트가 반복적으로 일하게 만드는 문제
3. **그래프 엔지니어링** — 여러 루프와 역할을 연결해 전체 시스템을 설계하는 문제

이 계단식 구조로 보면 헷갈림이 줄어듭니다.

## 언제 루프 엔지니어링이 더 맞을까
다음 같은 경우에는 루프 관점이 더 유용해 보입니다.

### 1. 한 에이전트가 대부분의 일을 끝낼 수 있을 때
- 코드 수정
- 문서 보완
- 반복 점검
- 테스트와 재시도

### 2. 핵심 문제가 ‘다음 행동을 스스로 이어 가게 하는 것’일 때
- 한 번의 응답이 아니라 계속 수행해야 함
- 실패 후 재시도가 중요함
- 종료 조건을 명확히 둘 수 있음

### 3. 구조보다 검증 루프가 더 중요할 때
- 작성 → 테스트 → 수정 → 재실행
- 분석 → 요약 → 체크 → 수정

이 경우엔 굳이 복잡한 다중 에이전트 구조보다, **좋은 목표·검증·재시도 루프**가 더 큰 효과를 냅니다.

## 언제 그래프 엔지니어링이 더 맞을까
반대로 다음 같은 경우에는 그래프 관점이 더 자연스럽습니다.

### 1. 역할 분리가 성능과 안정성을 높일 때
- 작성자와 검토자를 분리
- 검색 담당과 요약 담당을 분리
- 보안 검토와 기능 구현을 분리

### 2. 병렬화가 중요한 경우
- 여러 소스를 동시에 조사
- 여러 코드베이스를 동시에 탐색
- 여러 후보안을 만든 뒤 합치기

### 3. 승인·감사·정책 경로가 중요할 때
- 외부 API 호출 전 사람 승인
- 민감한 DB 작업 전 검토
- 특정 노드만 특정 도구에 접근 가능

### 4. 작업 흐름이 본질적으로 여러 단계의 협업일 때
- 분류 → 라우팅 → 실행 → 검증 → 보고
- 팬아웃(fan-out) → 팬인(fan-in) 구조
- 조건 분기와 재합류가 많은 시스템

이럴 때는 “한 에이전트를 더 똑똑하게 만들기”보다, **누가 어떤 일을 맡고 어떻게 연결되는지**를 설계하는 것이 더 중요해집니다.

## 두 개념을 표로 비교해 보면
| 항목 | 루프 엔지니어링 | 그래프 엔지니어링 |
| --- | --- | --- |
| 핵심 질문 | 에이전트가 어떻게 반복적으로 더 잘 일하게 만들까? | 여러 에이전트와 단계가 어떻게 함께 일하게 만들까? |
| 초점 | 반복, 검증, 재시도 | 역할 분리, 라우팅, 연결 구조 |
| 기본 단위 | 한 에이전트의 작업 사이클 | 여러 노드와 엣지의 전체 구조 |
| 대표 흐름 | 목표 → 실행 → 관찰 → 수정 → 반복 | 분류 → 위임 → 병렬 작업 → 합치기 → 승인 |
| 강점 | 단순하고 강력함, 구현이 쉬움 | 확장성, 병렬화, 책임 분리 |
| 위험 | 한 에이전트에 과부하 집중 | 구조가 과해지면 복잡성 폭증 |
| 어울리는 상황 | 한 명이 해도 되는 반복 업무 | 팀처럼 움직여야 하는 복합 업무 |

## 제가 이해한 실무적 결론
제가 이번에 조사하면서 얻은 가장 실용적인 결론은 이것입니다.

### 1. 대부분은 먼저 루프부터 잘 만들어야 한다
아직 많은 작업은 복잡한 다중 에이전트 그래프보다,

- 목표를 더 선명하게 주고
- 검증 기준을 붙이고
- 실패했을 때 다시 시도하게 만들고
- 상태를 남기게 하는 것

만으로도 충분히 좋아질 수 있습니다.

즉 **그래프를 꿈꾸기 전에 루프를 제대로 설계하는 것**이 먼저일 가능성이 큽니다.

### 2. 그래프는 ‘대단해 보이는 구조’가 아니라 ‘책임을 나누는 구조’여야 한다
그래프 엔지니어링이 멋있어 보인다고 해서 무조건 여러 에이전트를 붙이면, 오히려 관리 비용만 늘어날 수 있습니다.

진짜 가치가 있는 그래프는,

- 왜 이 노드를 따로 두는지
- 왜 이 단계는 병렬화하는지
- 왜 이곳에 사람 승인이 필요한지
- 어떤 상태만 다음 단계로 넘길지

가 명확할 때 나옵니다.

### 3. 루프와 그래프의 핵심은 결국 ‘좋은 제약’이다
둘 다 공통적으로 말하는 건 비슷합니다.

- 모델에게 모든 걸 맡기지 말고
- 어디는 자유롭게 맡기고
- 어디는 구조로 제한하고
- 어디는 검증으로 되돌리고
- 어디는 사람이 확인하게 하라

즉 두 개념 모두 결국은 **LLM의 자유도를 그냥 방치하지 않고, 일하는 구조로 다듬는 설계 기술**에 가깝습니다.

## 아직 헷갈리거나 조심해야 할 점
### 1. 유행어와 실질을 구분해야 한다
이 분야는 용어가 너무 빨리 늘어납니다. 어떤 글은 진짜 설계 문제를 잘 짚지만, 어떤 글은 기존의 워크플로 오케스트레이션이나 상태 머신 이야기에 새 이름을 붙인 정도일 수도 있습니다.

그래서 이름보다 중요한 건 항상 이것 같습니다.

- 반복 구조를 설계하고 있는가?
- 검증 루프가 있는가?
- 역할과 책임이 분리되어 있는가?
- 상태와 전이가 명시적인가?

### 2. 그래프 엔지니어링은 아직 용어 의미가 문맥마다 조금 다르다
어떤 글은 그래프 엔지니어링을 **멀티에이전트 조직 설계**로 보고,
어떤 글은 **루프들이 서로 감시·제약·수정하는 상위 구조**로 보고,
또 어떤 글은 **LangGraph류 프레임워크로 워크플로를 명시적으로 짜는 것**에 더 가깝게 씁니다.

즉 지금은 딱 하나의 보편적 정의보다, **공통 핵심만 잡아두는 편**이 현실적입니다.

그 공통 핵심은 아마 이것입니다.

> **그래프 엔지니어링은 한 개의 루프를 넘어서, 여러 단계·역할·루프를 연결한 전체 시스템 구조를 설계하는 관점이다.**

### 3. 구조가 좋아져도 검증 책임은 사라지지 않는다
Addy Osmani가 강조하듯, 루프가 돌고 그래프가 정교해져도 **“완료”는 주장이지 증명이 아닐 수 있습니다.**

즉,

- 자동화가 늘어날수록
- 검증 없는 낙관도 같이 늘어나기 쉽고
- 사람이 이해하지 못한 코드는 빨리 쌓일 수 있습니다.

그래서 루프와 그래프가 좋아질수록 오히려 더 중요해지는 건,

- 외부 검증 기준
- 리뷰 지점
- 실패 기록
- 사람의 최종 판단

같은 것들입니다.

## 내가 가져갈 포인트
- **루프 엔지니어링**은 한 에이전트가 목표를 향해 **행동 → 관찰 → 수정**을 반복하도록 만드는 설계다.
- **그래프 엔지니어링**은 여러 역할과 단계, 에이전트, 승인 지점을 **노드와 엣지의 구조**로 설계하는 관점이다.
- 둘은 경쟁 개념이 아니라, **루프가 더 작은 단위이고 그래프가 더 큰 구조**라고 보는 편이 이해가 쉽다.
- 대부분의 실무에서는 먼저 **좋은 루프**가 필요하고, 그다음 복잡성이 커질 때 **그래프 관점**이 필요해진다.
- 이름이 늘어나는 것보다 중요한 건, 결국 **검증 가능한 목표와 명시적인 작업 구조**를 만드는 일이다.

## 나중에 더 볼 것
- 실제 코딩 에이전트 작업 하나를 골라, 단일 루프로 충분한지 그래프 구조가 필요한지 비교해 보기
- 작성자/검토자 분리를 했을 때 품질이 얼마나 나아지는지 기록해 보기
- 상태를 어떤 형식으로 남길 때 장기 실행에 가장 도움이 되는지 실험해 보기
- LangGraph, OpenAI Codex, Claude Code, Hermes 같은 도구에서 각각 루프/그래프 관점이 어디까지 드러나는지 비교해 보기

## 작업 메모
이번에 정리하면서 느낀 건, 이 두 용어가 완전히 새로운 기술이라기보다는 **에이전트를 단발성 답변기가 아니라 ‘일하는 시스템’으로 보기 시작하면서 필요한 관점들이 더 세분화된 것** 같다는 점입니다.

예전에는 “프롬프트를 잘 쓸 것인가”가 중심이었다면, 이제는 점점

- 어떤 목표로 돌릴지
- 어떤 조건에서 멈출지
- 누가 검토할지
- 어떤 단계는 코드로 고정할지
- 어떤 단계만 모델에게 맡길지

같은 설계 질문이 더 중요해지고 있습니다.

그래서 루프 엔지니어링과 그래프 엔지니어링은 각각 다른 유행어라기보다, **AI 에이전트를 실제로 믿고 일에 붙이기 위해 사람들이 어디를 설계하고 있는지 보여 주는 표지판**에 더 가깝다고 느꼈습니다.
